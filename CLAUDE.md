# posgro (grocery-pos)

Offline-first grocery POS for the Uzbek retail market. Monorepo: Electron POS terminals (SQLite) + NestJS API on Contabo VPS (PostgreSQL) + Telegram bot. Owner/dev: Bobur (Fergana, UZ).

## Scope of this workspace

Server (`src/server`), web dashboard (`src/web`), landing (`src/landing`) **and the Electron POS** (`src/main`, `src/renderer`) are all in scope. POS work follows `.claude/rules/electron.md` and skill `ipc-feature`.

- **POS changes:** bump `package.json` version (`npm version patch --no-git-tag-version`), compile-check with `npx cross-env APP_MODE=pos electron-vite build`, and tell me to run `npm run deploy:pos` — I build and publish the installer, never you.
- **Still off limits:** `electron-builder.config.js`, `scripts/build-pos.js`, build outputs (`dist*`, `release`, `build`). Don't read build outputs; they burn context.
- **Old tills stay in the field.** Terminals update at different times, so the server must keep working with the previous POS release (N-1), and the new POS must tolerate a server that has not deployed yet. Rollout: server first (on `main`, deployed), then the installer. Every server change MUST stay backward compatible with the existing POS client:
  - never rename/remove/retype an endpoint, field, enum value, or status code the POS uses (`POST /api/sales/sync`, `GET /api/products?updatedAfter=`, `/api/auth/*`, `/api/health`);
  - new request fields optional; new response fields additive only;
  - `POST /api/sales/sync` must be idempotent (POS retries on failure) — dedupe on `(storeId, receiptNumber)` (not the terminal's local `id`, which can change after a SQLite reset), never insert twice.
- `src/shared/**` and `prisma/schema.prisma` are also compiled/generated by the Electron build. Ask before touching them; keep changes additive.
- At least one live store is running in production. Protecting it beats everything else.

## Hard rules

1. Migrations are **additive only**: new tables, new nullable/defaulted columns, new indexes. No drops, renames, type changes, or `NOT NULL` without default. Use expand → backfill → (much later) contract, contract in a separate approved release.
2. New behaviour goes behind a feature flag that **defaults to current behaviour**. No hard deletion of live functionality.
3. Never delete a Docker volume, run `migrate reset`, `db push`, `docker compose down -v`, or `DROP/TRUNCATE`. Prod data needs a verified backup-restore cycle first (`/pg-backup`).
4. Never read or print `.env*` (except `.env.example`), JWT secrets, bot tokens, DB passwords, or `.pfx/.pem` files. Never commit them.
5. Don't change `DB_USER`/`DB_PASSWORD` in `.env` for an existing Postgres volume (SCRAM mismatch). If auth fails, fix inside the running container with `ALTER USER`, not by wiping data.
6. Don't bind Postgres to `0.0.0.0` — Docker-published ports bypass UFW. Use `127.0.0.1:5432:5432` or no published port.

## Branch & release flow: dev first, then main

1. Work on a feature branch (`feat/…`, `fix/…`, `refactor/…`), never commit directly to `main`.
2. Merge/push to **`dev`** first. A push to `dev` auto-deploys **staging** (`.github/workflows/deploy-staging.yml` → `scripts/deploy/staging.sh`, API on `127.0.0.1:3002`, DB `posgro_staging`).
3. **Stop and wait for my confirmation** that it works on staging. Don't treat a green CI run as confirmation.
4. Only after I confirm: merge `dev` → `main` and push. Never push to `main` without that explicit OK, even if I approved the change itself earlier.
5. `main` goes to **production** automatically every night at 23:00 Tashkent (`.github/workflows/deploy.yml`, cron `0 18 * * *` UTC). Anything on `main` is live by the next morning, so `main` must always be deployable.

## Domain facts worth remembering

- Roles: `SUPER_ADMIN` (all stores, `storeId` null), `ADMIN` (store admin), `USER` (cashier), `CLIENT` (credit customer — no permissions, refused at every login). Auth = phone + password (bcrypt), JWT 8h. Guard stack: `JwtAuthGuard` + `RolesGuard` + `@Roles()`. Admin mutations write an `AuditLog` row.
- Money: `Decimal(10,2)`; quantities `Decimal(10,3)`. Never do float math on money — use Prisma `Decimal`/integers. REGOS wants **tiyin** (×100) and quantities ×1000.
- Uzbek compliance: MXIK/IKPU mandatory per product, `vat_value = -1` for non-VAT payers, asl-belgisi marking codes, OFD via ofd.soliq.uz. See skill `regos-vcr`.
- Infra: Contabo VPS (Ubuntu, Docker Compose, Nginx, Let's Encrypt), PostgreSQL **15** in prod (`postgres:15-alpine`, 15.17 verified on the VPS 2026-09-29), Cloudflare DNS. Prod DB on `127.0.0.1:5432`, staging DB on `127.0.0.1:5434`, API on `127.0.0.1:3001` (staging `3002`); only 22/80/443 are public.
- The VPS is **shared** with other projects (`hisob-app`, `yettibuloq-app` + its own Postgres, `telegram-bots-*` with Postgres 17). Scope every Docker command to the posgro compose project — never `docker system prune`, global restarts, or touching other containers/volumes.
- Telegram bot runs on the same VPS.
